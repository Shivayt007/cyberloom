# Cyberloom Link Inspector

Mobile-friendly website: paste any public HTML page containing Cyberloom short links, or paste one Cyberloom or MessyCloud URL directly. Discover up to eight Cyberloom links and inspect each separately, with live terminal messages, browser preview, and final MessyCloud download links. It does **not** download files or bypass CAPTCHA / access controls. It may not work if the shortener changes its flow or blocks automated browsers.

## EasyPanel deployment

1. Create a new **Project** and **App Service** in EasyPanel.
2. Source: **GitHub**, repository `Shivayt007/cyberloom`, branch `main`.
3. Build: **Dockerfile** (path: `Dockerfile`, build context `/`).
4. No `APP_PASSWORD` is required. Optionally copy `ALLOWED_START_HOSTS` and `TARGET_HOSTS` from `.env.example`.
5. Expose **port 8000** as HTTP and assign an EasyPanel domain with HTTPS.
6. Deploy. Paste a public source webpage URL or a direct Cyberloom link and click **Inspect Website**. Health endpoint: `/health`.

The website has no password by request. Keep the VPS behind HTTPS, apply firewall restrictions, and note that public visitors can consume Playwright CPU and RAM. Rate limits (12 starts per visitor per hour, 35 globally) and a single-browser semaphore provide basic protection; no arbitrary webpage receives a Playwright browser. Source-page discovery fetches only up to 2 MB of public HTML with redirects, timeout and public-only DNS validation. The Playwright browser runs as an unprivileged user; production browser hardening and container isolation remain your responsibility. The built-in image is large (~gigabytes) because it contains browsers.

**No EasyPanel auto-deployment is configured.** If your EasyPanel service enables auto-deploy on push, future updates can trigger that; otherwise click Deploy manually.

## Local development (desktop Linux/Windows, not Android)

```sh
pip install -r requirements.txt
python -m playwright install chromium
uvicorn app:app --host 127.0.0.1 --port 8000
```

## API

`POST /api/discover` with JSON `{"url":"https://example.org/page"}` returns `{"links":[...],"total":...}` with up to eight Cyberloom `/l/` URLs. `POST /api/inspect` with JSON `{"url":"https://www.cyberloom.best/l/abc123","timeout":120,"settle":12}` streams newline-separated JSON events for a single URL. Only one Playwright scan runs at a time per instance. No links are retained on server after completion.

## Notes

- No automatic CAPTCHA bypass or timer skipping. Countdown pages are allowed to run naturally.
- Some links inside frames or generated by network scripts may not be found.
- The external site's policies and your rights to access links still apply.

## When Stackmint requires human verification

Cyberloom may redirect to `stackmint.ink`, which can display an **I'm human** challenge. Headless Chromium cannot reliably pass this verification. The website now detects a visible verification prompt and stops early, showing an **Open Stackmint in my browser** link instead of waiting 120 seconds.

To continue, open the link in your normal browser, complete the human-verification step yourself, click **Continue to Destination**, then copy the final `messycloud.ink` URL into the inspector's input field and run again. The inspector also accepts permitted MessyCloud destination URLs directly. This process does not transfer browser cookies or verification state from your mobile browser to the VPS, and destination pages that require those may remain inaccessible to the headless browser. The app does not bypass access controls or CAPTCHAs.

## Redirect chains captured in the 2026-10-23 walkthrough

A phone recording showed Inkvoyage's "Continue to Destination" page, transient Indiatimes pages, a second MessyCloud "Continue to Destination" page, and finally a MessyCloud file page showing an **M1 DIRECT** server option. Those intermediate domains may change. The automation now reports all open tabs, only clicks Continue on known redirect hosts (Cyberloom, Stackmint, Inkvoyage, and MessyCloud), and does **not** stop merely because MessyCloud's hostname appears: it waits for the actual file page. It never attempts to defeat a CAPTCHA. Server buttons implemented solely through JavaScript may need an additional, site-specific extractor.

## When Stackmint stays on one tab

If the browser remains at `www.stackmint.ink/go?t=...`, the app now records browser-state diagnostics **after 18 seconds without navigation**, including page title, headings, visible buttons, iframe count, failed-resource hostnames, and an in-memory JPEG preview displayed below the terminal. The preview is streamed only to the active browser client and is not saved as a file on the server. Failed-resource counts and a blank preview help distinguish a loading problem from an access/verification gate.

The web app does not automate CAPTCHA, email sign-in, or other human-verification steps. Use the link shown in the UI to verify in your own phone browser, continue to the destination, and paste the final MessyCloud URL in the inspector. A verification cookie in your phone is not transferred to the VPS.

## Watch the VPS browser live

After clicking **Inspect Link**, the website displays **Live browser screen** below its terminal. The browser image automatically refreshes about every 2–3 seconds as the scanner loads pages, clicks Continue, changes tabs and reaches MessyCloud. A browser tab number and hostname appear above the picture. This is a low-frame-rate **read-only screenshot stream**, not an interactive VNC/WebRTC session or continuous video. The **Pause view / Resume view** control freezes or resumes the *local display*; it does not stop the scan or cease server-side capture.

Frames use the newline-delimited JSON response (`POST /api/inspect` with `live: true`), carry compressed JPEG data in memory, and are not written to disk. Screenshots may show untrusted third-party website content, including sensitive data; serve the site over HTTPS and avoid exposing sensitive URLs in public. Larger image traffic and lower frame rates are possible on a slow VPS or mobile connection.

To see it, redeploy the latest `main` branch in EasyPanel and start a new scan. No extra ports are necessary; HTTP container port 8000 is unchanged. If the site requires a human verification step, the screen will show it but cannot automatically solve it.

## Direct Continue URL discovered in page HTML

Some Stackmint/Inkvoyage Ready screens show an anchor like `<a id="cta" href="https://www.cyberloom.best/out?t=...">Continue to Destination</a>`. The page may also put a full-screen `div` above the control that intercepts normal pointer clicks. The inspector now reads **the actual current `href`** from that displayed link after the page shows **Ready!**, validates that it is an HTTPS Cyberloom `/out` URL with a nonempty `t` parameter, and follows it **in the same browser context**. The token is not hard-coded: it can change for every inspection. It still follows normal server-side redirects and does not forge a human-verification result.

If a visible human-verification challenge is present, the existing manual verification handling takes priority. If the `#cta` link is missing or invalid, the ordinary Playwright clicking/diagnostic logic remains available. The next browser URL is logged in the Live Terminal.

## M1 DIRECT file-server extraction

After the inspector reaches the final MessyCloud file page, it now looks for **[M1] DIRECT** links in regular anchor `href` attributes, related data URL attributes and accessible nested elements. Recognized links appear first in the results and in a separate **M1 Direct Download Link** section with a Copy button. It preserves the complete signed CDN URL (including `token` and `exp` query parameters) when copying. Terminal logs redact query strings to avoid unnecessarily exposing temporary access tokens. It does not download file contents or generate new tokens.

Some pages create the actual file URL only after executing button-specific JavaScript. That case is not guaranteed: this implementation extracts URLs already made available in the accessible page DOM or markup and would need the page's exact M1 element implementation for further support. Signed URLs may expire and should be used promptly.

## Collect all links on the final MessyCloud page

The final-page inspector now gathers all discoverable links from ordinary anchor `href` attributes, server/download buttons, supported `data-*` URL attributes, inline `onclick` URLs and the accessible DOMs of embedded frames. It additionally searches HTML markup for direct file URLs (without fetching those files). The result area is **All MessyCloud links**, with **All links**, **Download / Servers**, and **Other links** filters and a **Copy all links** action. **[M1] DIRECT** still has its own prominent Copy button.

Duplicate URLs are combined, and labelled server links take precedence when the same URL appears in multiple HTML locations. Signed `token`/`exp` parameters are preserved in links copied from the UI but hidden in diagnostic terminal messages.

Limitations: no downloader, no execution of arbitrary inline JavaScript, and no CAPTCHA bypass. Links generated only by a future click or authorized API response might not exist in the page yet, so those cannot be guaranteed by static DOM extraction. Results are capped at 250 URLs per scan.

## Connection reliability and batch retry

The frontend **no longer holds one network stream open for the entire batch**. It calls `POST /api/discover` once and opens `POST /api/inspect` **separately for each Cyberloom link**. When a network error interrupts one link, the website retries **only that link once**, waiting a few seconds before retrying. Previously completed MessyCloud destinations and M1 links remain visible in the results area. If a link still fails, **Retry failed links** appears, so you can manually retry only the unsuccessful entries without rerunning earlier successes. Results are held in the active browser page, not persisted in the VPS database or across a page refresh.

This approach reduces the chance of mobile network/proxy timeouts during several inspections. A dropped connection to a single scan can still fail, and expiring signed CDN URLs may stop working independently of the scanner.

## Source page title and poster extraction

When you enter a public source webpage containing Cyberloom links, the **Source post details** card now extracts the visible forum post title from `h1.ipsType_pageTitle .ipsType_break.ipsContained > span` and the main poster URL from `img.ipsImage_thumbnailed[src]`. For example, this supports IPS Community Suite forum topics with the long movie name and a Twitter-hosted thumbnail image. If the exact markup is missing, the extractor can use `og:title` and `og:image` metadata where present.

The UI shows the post/movie title and the poster URL, each with its own **Copy** button, as well as a lazy-loading image preview. HTML-escaped image query strings such as `&amp;name=large` are decoded so the copied URL retains normal `&name=large`. Metadata is returned from `POST /api/discover` and stays available alongside the batch's Cyberloom and MessyCloud results. The scanner reads the source page HTML without downloading the poster to the VPS.

This metadata appears when you enter a source webpage, not when you enter a Cyberloom short URL directly; shorteners don't necessarily contain the original forum title or poster. Pages that render the title and image only after running JavaScript may not expose them to the HTML-only source discovery step.
